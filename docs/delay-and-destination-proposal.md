# آلية التأخير وتغيير الوجهة

نُفذ الانتظار وتغيير الوجهة بطلب المستخدم في 19 أكتوبر 2026. راجع [الانتظار والمفاوضة](waiting-and-negotiation-2026-10-19.md) و[تغيير المسار والتقارير](route-change-and-waiting-reports-2026-10-19.md) للآلية المنفذة والتحقق. النص أدناه يحتفظ بالمقترح السابق للمرجعية؛ الأرقام أمثلة وليست أسعارًا معتمدة.

## توقف بطلب الراكب

لا يكفي ثبات GPS لإثبات أن الراكب سبب التأخير؛ قد تكون إشارة مرور أو ازدحامًا أو GPS ضعيفًا. يمكن للتطبيق اقتراح «هل هذا توقف بطلب الراكب؟» بعد ثبات معتبر بموقع حديث ودقة مناسبة، لكن لا يبدأ احتساب رسوم تلقائية بسبب هذا الاستنتاج وحده.

1. يضغط السائق «توقف بطلب الراكب»، فيعرض التطبيق السبب والموقع ويرسل طلبًا إلى API. يجوز أيضًا أن يبدأ الراكب طلب التوقف من تطبيقه.
2. تظهر للراكب سياسة واضحة قبل الموافقة: مهلة مجانية، سعر الدقيقة بعدها، سقف الرسوم، وكيفية إنهاء التوقف. تُسجّل الموافقة والحالة في الخادم. عند رفض الراكب لا تبدأ رسوم انتظار جديدة؛ يبقى التواصل والدعم لحل الخلاف.
3. بعد قبول الطرف المطلوب، يبدأ توقيت الخادم. مثال قابل للنقاش: دقيقتان مجانًا ثم 50 ر.ي للدقيقة باحتساب الثواني؛ 5 دقائق إجمالي توقف = 150 ر.ي زيادة. تعرض الواجهتان المؤقت و«الأجرة الأصلية + الانتظار = الإجمالي الحالي»، مع تنبيه قبل نهاية المهلة وعند بدء الرسوم.
4. يضغط السائق «استئناف الرحلة»، ويرسل API وقت النهاية المؤكد. الحركة الموثوقة يمكنها إيقاف عداد الانتظار بعد تحقق زمني ومكاني، لتجنب استمرار الرسوم إذا نسي الزر؛ تتجنب العينة المنفردة إنهاءه بسبب اهتزاز GPS.
5. تُحفظ الرسوم مرة واحدة كسطر مستقل في تفاصيل الأجرة. يبث API السعر الجديد للطرفين ولوحة الإدارة، ويصبح المبلغ نفسه أساس شاشة التحصيل. أي تعديل إداري لاحق يحتاج سببًا وسجل تدقيق.

التوقيت مصدره الخادم مع معرف عملية ومنع تكرار الطلب وقفل حالة الرحلة. لا يبدأ توقف ثانٍ فوق توقف مفتوح. عند فقد GPS أو الاتصال لا تستنتج المنظومة تأخيرًا جديدًا؛ تُعرض حالة المزامنة، وتُحد الرسوم المستمرة بسقف وسياسة اتصال متفق عليها. لا تُحتسب مدة التوقف مرتين كزمن قيادة وانتظار.

**ما يفعله السائق:** طلب بدء التوقف، الاطلاع على موافقة الراكب والمؤقت، ثم الاستئناف. لا يُدخل مبلغًا يدويًا. يوضح التطبيق للطرفين متى بدأت الرسوم ومتى توقفت وكيف حُسبت.

## تغيير الوجهة أثناء الطريق

1. يختار الراكب «تغيير الوجهة»، ويحدد المكان الجديد. يحتفظ النظام بالوجهة الحالية حتى اعتماد التغيير.
2. يأخذ API لقطة حديثة لموقع السائق ونقطة التغيير، ويحسب الطريق المتبقي للوجهة الجديدة والمسافة والزمن؛ يعيد عرضًا قصير الصلاحية يشمل السعر السابق والجديد والفارق وتفصيل الرسوم.
3. يوافق الراكب على السعر، ويقبل السائق المسار الجديد قبل تفعيله. عند رفض السائق أو انتهاء العرض تبقى الرحلة الأصلية. إذا ابتعدت المركبة كثيرًا أثناء انتظار القرار يعاد حساب العرض ويطلب تأكيد السعر المحدث.
4. عند الاعتماد يحفظ API الوجهة الجديدة والسعر وإصدار الرحلة في معاملة واحدة، ثم يبث التغيير. يعيد تطبيق السائق حساب الملاحة من موقعه الحالي، وتعرض خريطة الراكب والمشاركة والإدارة الوجهة الجديدة. تُحفظ الوجهة والسعر السابقان في سجل التغييرات.

### احتساب الأجرة

المطلوب تجنب احتساب الرحلة كاملة من البداية مرة أخرى، وتجنب شحن ما لم يُقطع من الوجهة القديمة:

**الإجمالي الجديد = الجزء المقطوع المؤكد + تكلفة الجزء المتبقي إلى الوجهة الجديدة + رسوم الانتظار المعتمدة + الرسوم الثابتة مرة واحدة.**

لأن التطبيق يدعم التفاوض على سعر إجمالي، يجب تثبيت سياسة توزيع هذا السعر عند قبول الرحلة. اقتراح: فصل الرسم الثابت، وحفظ قواعد الكيلومتر/الدقيقة وإصدار التسعير، ومعامل تفاوض يربط السعر المقبول بالتقدير الأصلي. يطبق المعامل نفسه على الجزء المقطوع والجزء المتبقي الجديد؛ لا تدخل سياسة تسعير أحدث في منتصف الرحلة ولا تتكرر الرسوم الثابتة. وقد تنخفض الأجرة عند تقصير الوجهة، بشرط ألا تنخفض عن الجزء المنفذ والرسوم المعتمدة.

مثال توضيحي: المنفذ 600 ر.ي، المتبقي الجديد 800 ر.ي، الانتظار المعتمد 150 ر.ي، الرسم الثابت 100 ر.ي؛ الإجمالي الجديد 1650 ر.ي. إذا سبق التحصيل أو فُتح طلب دفع، يجب تسوية الحالة في الخادم أولًا، ولا يُسمح بتحصيل مبلغ قديم بالتوازي مع تعديل الوجهة.

**ما يفعله السائق:** يراجع الوجهة والمسافة والأجرة الجديدة، ثم يقبل أو يرفض؛ عند القبول تتحول الملاحة تلقائيًا. لا ينهي الرحلة ولا ينشئ رحلة ثانية ولا يعدل المبلغ بنفسه.

## قرارات مطلوبة لاعتماد السياسة

- مقدار المهلة المجانية وسعر دقيقة الانتظار وسقفها، وهل تختلف حسب الخدمة.
- سياسة فقد الشبكة أثناء توقف مدفوع، وحد الثبات ودقة GPS وزمن الحركة اللازمة لإنهائه.
- اعتماد معامل التفاوض المذكور أو اختيار سياسة تسعير أخرى صريحة، مع قاعدة تخفيض السعر عند تقصير الوجهة.
- اشتراط موافقة السائق على الوجهة الجديدة، ومهلة العرض والحد الذي يوجب إعادة حسابه بعد تحرك المركبة.
- سياسة الرحلات التي حُصّلت أجرتها بالفعل قبل التغيير، وآلية الاعتراض لدى الإدارة.

بعد اعتماد هذه القواعد يصبح التنفيذ دفعة واحدة عبر API وقاعدة البيانات ولوحة الإدارة والتطبيقين والإشعارات والمشاركة والتحصيل، مع اختبارات التكرار والتزامن وانقطاع الشبكة.
