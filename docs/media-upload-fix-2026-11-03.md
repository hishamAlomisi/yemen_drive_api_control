# إصلاح رفع الصور — 3 نوفمبر 2026

كان `POST /api/media/upload` يفشل بخطأ HTTP 500 قبل تنفيذ معالج الرفع: يضيف ربط `IFormFile` في Minimal API بيانات antiforgery تلقائياً، ولا توجد middleware لهذه الحماية في التطبيق.

أضيف `.DisableAntiforgery()` إلى مسار الرفع وحده في `src/YemenDrive.Api/Program.cs`. لا يستخدم الخادم مصادقة Cookies، ويرسل نموذج الإدارة الملف باسم `file` مع Bearer عبر `adminFetch` دون رمز antiforgery. لا يتطلب الإصلاح أي تغيير في التطبيقين أو الدومين أو ترحيل قاعدة بيانات.

صلاحيات المسار الحالية لم تتغير: الطلب دون Bearer يمر، وBearer غير الصالح يُرفض. لم يضف هذا الإصلاح حارس صلاحيات للرفع أو فحص محتوى الصور أو حدوداً جديدة للحجم؛ هذه مواضيع منفصلة مسجلة في التدقيق السابق.

## التحقق

اختبار `tests/media-upload-smoke.ps1` يرسل HTTP فعلياً إلى نسخة مستقلة من حزمة Windows، على loopback ودون قاعدة بيانات أو Cookies أو رمز antiforgery. تضمن الاختبار العام للحزمة تشغيل الملف التنفيذي والملفات الثابتة وحراس الإدارة والتتبع، ثم استدعى فحوص الرفع.

| امتداد PNG بأحرف كبيرة | 500 | 200 ومحتوى مطابق |
| ملف فارغ | 500 | 400 |
| امتداد غير مدعوم | 500 | 400 |
| حقل الملف مفقود | 500 | 400 |
| اسم حقل خاطئ | 500 | 400 |
| Content-Type غير multipart | 415 | 415 |
| Bearer غير صالح | 401 | 401 |

فحص عدم إعداد قاعدة البيانات نجح أيضاً: تسعة فحوص رفع/تمهيد ناجحة في النسخة المصححة. الطلبات المرفوضة لم تضف أو تعدل ملفات في مجلد الرفع. نجحت فحوص الحزمة العامة الاثنا عشر، ومنها مجموعة فحوص الرفع. سجل الحزمة المصححة لا يحتوي استثناء antiforgery أو `fail:`.

صُحح توقع الاختبار الأولي للـContent-Type غير المناسب من 400 إلى استجابة ASP.NET الحالية 415 مع السماح بجسم استجابة فارغ؛ أعيد الاختبار على الحزمتين، ولم تتغير الشيفرة التشغيلية لهذا السلوك. النتيجة النهائية للحزمة السابقة: ستة فحوص تعيد 500 وتفشل، وثلاثة فحوص تنجح. احتُفظ بنتائج المحاولة الأولية كذلك.
