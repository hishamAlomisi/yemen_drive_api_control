# تحويل المحافظ وإصلاح التقييم — 2 نوفمبر 2026

أضيف زر «تحويل لحساب» إلى شاشة محفظة الراكب والقائمة الجانبية. يدخل الراكب رقم المستلم والمبلغ والملاحظة، ثم يعرض الخادم بيانات المحفظة المختصرة بعد التحقق من كفاية الرصيد للمبلغ والرسوم. تظهر بطاقة تأكيد من أسفل تتضمن اسم المستلم ونوعه (عميل/سائق) والهاتف والمبلغ والرسوم والملاحظة والإجمالي. يليها تأكيد كلمة مرور الحساب في نافذة وسط الشاشة ثم فاتورة التحويل. تدعم الشاشة الأرقام العربية وإعادة فتح الفاتورة من سجل التحويلات أو حركة المحفظة الصادرة.

تحفظ مرجعية التحويل المعلق محلياً لحساب الراكب لاستعادتها بعد إعادة التشغيل أو انقطاع الاتصال؛ لا تحفظ كلمة المرور. يتأكد التطبيق من النتيجة بعد فقدان استجابة التأكيد، ويعيد استخدام العملية نفسها. صلاحية عرض التأكيد خمس دقائق، مع إعادة فحص رصيد المرسل وحالة المستلم عند التنفيذ.

## الرسوم والإدارة

توجد شاشة «رسوم تحويل المحافظ» تحت إدارة النظام في لوحة التحكم. لكل شريحة حد أدنى شامل وحد أعلى غير شامل، ويمكن ترك الحد الأعلى فارغاً. تحدد الرسوم كقيمة ثابتة بالريال اليمني أو نسبة من المبلغ، وتقرّب النتيجة إلى منزلتين عشريتين. يمكن تحديد قيمة صفر صراحةً للتحويل المجاني. تمنع الشرائح المفعلة المتداخلة، ويمكن إيقاف الشريحة أو تعديلها. لا يحذف تعديل الرسوم الفواتير السابقة؛ تحفظ كل فاتورة أساس رسومها وقيمتها عند عرض التأكيد.

لا توجد رسوم افتراضية مفترضة: يلزم إضافة شريحة مفعلة تغطي المبلغ لتفعيل التحويل. تحتاج المشاهدة إلى `finance.read`، والحفظ إلى `finance.write`.

## القيد المحاسبي

تنفذ تغييرات المحفظتين والحركات والفاتورة والقيد في معاملة SQL واحدة بمستوى عزل Serializable. الخصم هو المبلغ زائد الرسوم، والمستلم يقيد له المبلغ وحده. مثال تحويل 1000 ورسوم 20:

| الحساب | مدين | دائن |
|---|---:|---:|
| التزام محفظة المرسل | 1020 | 0 |
| التزام محفظة المستلم | 0 | 1000 |
| 4110 — رسوم تحويل المحافظ | 0 | 20 |

المرجع فريد، والتأكيد المتكرر لا ينشئ خصماً جديداً. يمنع التحويل للنفس أو لمحفظة غير متاحة أو مختلفة العملة. لا تكشف استجابة البحث رصيد المستلم أو بياناته الخاصة. خمس محاولات كلمة مرور خاطئة توقف التأكيد لمدة 15 دقيقة على مستوى محفظة المرسل.

الـAPI يستخدم `WalletTransferModel` بعمليات `quote`, `confirm`, `get`, `list`، و`WalletTransferFeeModel` بعمليات `list`, `add`, `update`. جميعها عبر مسار التنفيذ الحالي مع جلسة المستخدم. التأكيد يقبل مرجع العرض وكلمة المرور فقط؛ يعتمد المبلغ والمستلم والرسوم المحفوظة في الخادم.

## إصلاح تجمد التقييم

أعيد إنتاج العطل عند وصول إنهاء الرحلة أثناء عرض شاشة الدفع: كان استبدال المسارات يحذف PaymentController المرتبط بالشاشة السابقة ويترك عناصر التقييم مرتبطة بحالته القديمة. أصبح للتقييم متحكم مستقل بالوسم `ride-review`، تتبعه النجوم والأوصاف والتعليق والإرسال. نجح اختبار الانتقال المباشر واختيار أربع نجوم وإضافة وصف وإرسال التقييم دون إعادة تشغيل التطبيق.
