# دفع الرحلات عبر فلوسك وجيب

تحديث 2 نوفمبر 2026: تطبق [التصحيحات التشغيلية](operational-corrections-2026-11-02.md) على الشروط القديمة أدناه. انتهاء النقل مستقل عن الدفع، ويُحصّل المتبقي فقط. يسمح بالانتظار وتعديل الوجهة بعد الدفع المسبق مع تسوية الفرق؛ تبقى المحاولات المجهولة محجوزة حتى تتأكد نتيجتها. نجاح التسوية يغلق المحاولة ويثبت قبضاً واحداً. الاسترداد إلى محفظة التطبيق يتطلب موافقة الراكب، ورفضها يفتح معالجة بديلة مع الإدارة.

يستخدم API جلسة الوكيل المحفوظة لكل طريقة دفع من إعدادات الإدارة، وعمليات السحب من حساب العميل في `eqsWallets 0.10.0`. يدعم `Floosak` و`Jaib` فقط حالياً. لا يرسل التطبيق رقم العميل أو المبلغ أو العملة إلى API: تؤخذ من المستخدم المصادق عليه ومن إجمالي الرحلة المثبت، بما فيه رسوم الخدمة والانتظار. العملة وعملة الرسوم `YER`. يُطبّع الرقم اليمني إلى `9677xxxxxxxx` لفلوسك، وإلى الرقم المحلي ذي التسعة أرقام `7xxxxxxxx` لجيب، حتى لو كان الرقم المحفوظ يبدأ بـ`+967` أو `00967`.

يبدأ الدفع الإلزامي بعد قبول عرض السائق إذا اختيرت وسيلة غير نقدية عند الحجز. ويمكن إتاحة الدفع للراكب أثناء الرحلة أو بعد اكتمالها وفق حالة الرحلة. يلزم أن تكون طريقة الدفع المختارة نشطة ومتاحة للرحلات، وأن يكون حساب وكيلها متصلاً وحساب التسوية ومحفظة السائق مجهزين بالريال اليمني. يتحقق المزود من حساب العميل وصلاحية السحب؛ لا يفترض API وجود رصيد كافٍ من بيانات التطبيق. يحفظ سجل العملية هوية المزود وطريقة الدفع وإصدار جلسة الوكيل، ولا يمكن تحويل العملية المفتوحة إلى مزود أو حساب وكيل آخر.

فحص مكتبة فلوسك الحالي لا يعيد رصيد العميل في استجابة التحضير، ورصيد الوكيل لا يمثل رصيد العميل. لذلك لا يمكن ضمان فحص الرصيد قبل شاشة التأكيد؛ يعتمد اعتماد الخصم على استجابة فلوسك النهائية ويعرض خطأ نقص الرصيد عند وروده. أكد فحص المكتبة دون اتصال تطبيع `YER` وتوثيق اسم العميل وبناء إيصال السحب عند النجاح.

لا ينفذ API طلباً منفصلاً لفحص رصيد العميل. إذا رفضت فلوسك السحب بسبب الرصيد، تُعرض نتيجة المزود بصياغة مثل «أفادت فلوسك بأن رصيد حسابك لا يكفي لإتمام السحب بالمبلغ والعمولة المطلوبة». وإذا حدد المزود أن النقص في رصيد الوكيل، تُنسب المشكلة إلى حساب الوكيل دون نسبتها للراكب.

تُصاغ رسائل المزود التجارية بالعربية باسم المزود المختار اعتماداً على نص `WalletStepResult.Message` وكود الخطأ، بما فيها نقص الرصيد، الحساب غير المسجل أو الموقوف، الرمز غير الصحيح أو المنتهي، وحدود السحب. يوضح النص المحدد سبب الأخطاء العامة مثل `Rejected`؛ وتبقى الرسائل العربية التجارية غير المعروفة ظاهرة بعد تنقيتها. للنص الإنجليزي غير المعروف يُعرض شرح عربي مع التفصيل الأصلي الآمن، ولا تُختلق ترجمة لمعنى غير معروف. يحفظ `ProviderMessageAr` الرسالة المصاغة فقط كي تعود الرسالة نفسها بعد إعادة فتح الشاشة أو طلب `GET`، بطول أقصى 600 محرف. لا يحفظ النص الخام أو الرموز أو بيانات دخول الوكيل أو JSON أو تفاصيل الاستثناءات. الكلمات الواردة في رسالة المزود لا تغيّر الحالة المالية؛ تبقى إرشادات الانتظار أو المراجعة ظاهرة عند غياب تأكيد مالي موثوق حتى لو قال النص «نجاح».

## تشخيص تحضير فلوسك

يستخدم الربط `RequestWithdrawFromCustomerAsync`: يعيد طلب `offline_cashout` بيانات العميل قبل الموافقة وإرسال OTP. أثبت اختبار HTTP محاكى يستخدم DLL الفعلية انتقال بيانات العميل إلى `AwaitingConfirmation` دون استدعاء Save أو Confirm. يتبع رقم فلوسك الصيغة الدولية الموثقة؛ لا يغيّر الربط المرجع أو صيغة الهاتف لإعادة محاولة طلب غير محسوم.

في مراجعة 2026-10-30 تطابقت بيانات دخول الـAPI والتطبيق التجريبي، لكن الرد الأصلي لتحضير العملية المتوقفة لم يكن محفوظاً، ولذلك لم يثبت سبب فشلها. لا يثبت رد الاستعلام «المعاملة غير موجودة» عدم وصول طلب التحضير. يسجل الكونسول الآن `Wallet preparation response` مع رقم طريقة الدفع والمرحلة `Request` وحالة HTTP وأنواع حقول العقد المعروفة فقط، لتحديد الرفض أو الحقول الغائبة/غير المطابقة عند التجربة التالية. لا يسجل جسم الرد أو الرسائل أو أسماء الحقول غير المعروفة أو بيانات العميل أو رموزه. هذه البيانات تشخيصية فقط ولا تغيّر القرار المالي أو ترفع حجز عملية غير محسومة.

## مسار الراكب

في معالجة 2026-10-31 يحول الربط رد HTTP 422 المنظم للتحضير (رسالة وحقل `errors` دون بيانات نجاح) إلى رفض للطلب، مع عرض رسالة المزود بعد تنقيتها، بدلاً من إبقاء محاولة رفض التحقق معلقة. لا تعاد بيانات عميل مختلقة عند رفض المزود. يمكن الراكب إعادة طلب بيانات الحساب للمحاولة القديمة التي يسمح الخادم بإلغائها قبل OTP: يلغي التطبيق الحجز أولاً، ثم يبدأ طلباً جديداً بمرجع جديد. لا يعيد هذا الإجراء إرسال خصم غير محسوم.

يعرض السائق `selectedPaymentMethodNameAr` لاختيار الراكب، و`paymentMethodNameAr` للوسيلة التي سددت فعلياً. عند فتح التحصيل لطريقة غير نقدية تظهر شاشة حالة الدفع بدلاً من نموذج النقد، وتستقبل تأكيد السداد لحظياً. يعيد نموذج النقد قراءة الاختيار قبل الإرسال، ويرفض الخادم `DriverCashPaymentModel/add` إن لم يحدد الراكب النقد. لا يعمل زر إنهاء الرحلة إلا بعد `paymentCompleted=true`، ويتحقق الخادم من الدفعة المحفوظة تحت قفل الرحلة قبل اعتماد الإنهاء.

إذا اختار الراكب محفظة يمن درايف أو محفظة خارجية عند الحجز، تفتح شاشة الدفع الإلزامية مباشرة بعد قبول عرض السائق. يسمح الخادم بالدفع في حالات تعيين السائق والطريق والوصول، ويمنع بدء الرحلة حتى تسديدها أو تحويلها إلى النقد. تعرض الشاشة النقد ومحفظة يمن درايف والمحافظ الخارجية المتاحة. يمكن تغيير الوسيلة قبل التسديد؛ يؤكد الخادم الاختيار الجديد قبل بدء الدفع، ويحافظ على إلزام الدفع قبل بدء الرحلة عند اختيار محفظة أخرى. تستعاد البوابة عند إعادة فتح التطبيق أو وصول تحديث الرحلة، وتظل صفحة سبب إلغاء الرحلة متاحة.

التحويل إلى النقد قبل بدء الرحلة لا يسجل تحصيلاً؛ يتولى السائق التحصيل في مساره المعتاد. لا يسمح بتحويل الوسيلة أثناء اتصال بالمزود جارٍ أو خصم غير محسوم. يحدد الخادم `canCancel` للمحاولات التي يمكن إغلاقها: انتظار التأكيد/الرمز، أو تحضير فلوسك المتوقف في `Request` بخطأ `provider_failed` أو `outcome_unknown` قبل إرسال الرمز، دون أي مرجع أو دليل دفع. لا يشمل الاستثناء جيب، أو المراحل اللاحقة، أو إيصالات غير مطابقة. إلغاء المحاولة أو تغيير الوسيلة أو إلغاء الرحلة يغلق هذا الحجز تحت قفل الرحلة نفسه دون طلب مزود إضافي. إلغاء الرحلة غير المدفوعة أثناء توجه السائق أو بعد وصوله مباشر؛ حالتا تعيين السائق والرحلة الجارية تتبعان مسار مراجعة الإلغاء المعتاد. تعرض الواجهة سبب الرفض الفعلي من الخادم. بعد الدفع الإلكتروني يختفي تمكين الدفع والتحصيل من تطبيق السائق ويظهر اسم الوسيلة المدفوعة، وتعود شاشة الراكب إلى متابعة الرحلة حتى ينهيها السائق. لا تضاف رسوم انتظار جديدة على رحلة مسددة مسبقاً.

1. يختار الراكب فلوسك أو جيب ثم التالي. ينشئ الخادم حجزاً دائماً للدفع قبل الاتصال بالمزود.
2. تعاد بيانات العميل الموثقة من المزود: الاسم، الهاتف، المبلغ، العمولة إن كانت معلومة، العملة، والمستلم «يمن درايف». لا تعاد بيانات الوكيل أو استجابة المزود الخام.
3. تأكيد الراكب يستدعي `ConfirmAsync` للمحفظة المختارة؛ في فلوسك يطلب إرسال الرمز، وفي جيب يعتمد بيانات التحضير محلياً لأن طلب التحضير أرسل OTP بالفعل. عند طلب الرمز في `NextAction` تظهر شاشة إدخاله. الرمز يصدر من المزود المختار، ولا يحفظ في قاعدة البيانات أو السجلات.
4. يتابع التطبيق العملية نفسها ويمنع النقر المتكرر. بعد نجاح الخصم النهائي وحفظ التسجيل المحاسبي تظهر الفاتورة.

`Success` في نتيجة المكتبة يعني نجاح الخطوة فقط. النجاح المالي يتطلب `OperationStatus.Succeeded` مع إيصال مطابق لمبلغ الطلب وعملته ومرجعه. الرسوم التي يحددها المزود تعرض للعميل وتحفظ مع العملية، ولا تسجل إيراداً للمنصة أو تخصم من محفظة يمن درايف الداخلية.

السحب من حساب عميل جيب يستخدم `RequestWithdrawalAsync` دون مرجع سحب سابق لدى العميل. يرسل `PCashoutInitial` رقم الهاتف المحلي مثل `774922225` ومبلغ الرحلة، ويعيد `walletName` و`walletMobile` والرسوم و`trnID` لتأكيد بيانات العميل؛ إرسال OTP جزء من هذا التحضير. تستدعي موافقة الراكب `ConfirmAsync` محلياً وتظهر شاشة الرمز دون إعادة التحضير أو إرسال طلب رصيد أو OTP إضافي. بعد إدخال الرمز يستدعي `CompleteAsync` مسار `PCashoutConfirm` بمعرف `trnID` ومرجع الطلب الأصلي، ثم يمر النجاح المالي المثبت إلى التسوية المحاسبية المشتركة. اختبار HTTP محاكى بالمكتبة الفعلية يثبت ترتيب الطلبات والبيانات والحفاظ على المرجع ومنع تكرار الخصم وعدم فتح شاشة الرمز بعد رفض التحضير.

يتبع التكامل `NextAction` فعلياً، ويدعم طلب OTP أو PIN أو قسيمة قبل التأكيد إن أعاد المزود ذلك. في هذه المرحلة المبكرة يكون `customerIsProviderVerified=false` والاسم غير معروض كبيانات موثقة؛ نجاح خطوة الرمز وحدها لا يعني نجاح الخصم. لا يُنشأ رمز محلي بديل لرمز المحفظة. ملفات المكتبة في الخادم تطابق إصدار `net8.0` الموزع؛ اختلافها عن تطبيق المثال المبني لـFramework 4.8 لا يستدعي استبدالها بملفات هدف مختلف.

يرفض رد HTTP 422 المنظم في تأكيد فلوسك العملية حتى عند غياب `is_success`: تُقرأ رسالة المزود وحقول `errors` النصية أو مصفوفات النصوص، ومنها OTP غير المطابق أو الناقص، وتعود الحالة `Failed` مع إغلاق حجز الدفع وإتاحة اختيار وسيلة أخرى. نتيجة `OperationStatus.Failed` من المكتبة لا تتحول إلى مراجعة بسبب كود خطأ غير معروف للتطبيق. النصوص وحدها، أو تعارض بيانات النجاح والرفض، أو انقطاع الرد بعد الإرسال لا تثبت نتيجة مالية. الحروف في OTP فلوسك تُرفض محلياً قبل الإرسال، وتظل محاولة الرمز متاحة للتصحيح أو الإلغاء.

## المسارات

تطبع أرقام OTP العربية إلى ASCII قبل حجز خطوة الإكمال، وترفض الصيغ غير الرقمية دون إرسال طلب مزود أو تغيير حالة العملية. إذا أعادت DLL خطأ `InvalidRequest` محلياً مع `NextAction=OneTimePassword` والجلسة والمرجع والعميل والإيصال غير المكتمل المطابقة، يحتفظ الخادم بحالة `AwaitingCode` لتصحيح الرمز في الطلب نفسه. لا تسجل هذه النتيجة دفعاً ناجحاً ولا تغلق الحجز كخصم مكتمل.

كل المسارات مقيدة بالراكب صاحب الرحلة وتعيد غلاف `ApiResult` مع `Cache-Control: no-store`:

| الطلب | المدخلات | النتيجة |
| --- | --- | --- |
| `GET /api/rides/{rideId}/wallet-payment` | لا شيء | آخر عملية، أو `data: null` |
| `POST /api/rides/{rideId}/wallet-payment` | `{ "paymentMethodId": 1 }` | إنشاء العملية أو استرجاع العملية المفتوحة نفسها |
| `POST /api/rides/{rideId}/wallet-payment/{paymentId}/confirm` | `{ "approved": true }` | طلب الخطوة التالية؛ `false` يلغي قبل إرسال الرمز |
| `POST /api/rides/{rideId}/wallet-payment/{paymentId}/complete` | `{ "code": "..." }` | إكمال خطوة الرمز لدى المزود |

بيانات العرض: `id`, `rideId`, `paymentMethodId`, `providerCode`, `providerName`, `status`, `nextAction`, `canCancel`, `customerIsProviderVerified`, `customerName`, `mobile`, `amount`, `fees`, `feesKnown`, `currency`, `feeCurrency`, `recipient`, `providerReference`, `message`, `paidAtUtc`.

حالات العرض: `AwaitingConfirmation`, `AwaitingCode`, `Processing`, `Succeeded`, `Failed`, `Cancelled`, `ReviewRequired`. تتبع الواجهة `nextAction` ولا تتخطى تأكيد البيانات. لا يعني غياب قيمة العمولة أنها صفر.

## التسجيل والحماية من التكرار

يحفظ جدول `PaymentWalletOperations` مرجع الطلب، حالة الخطوة ونتيجة المزود والبيانات الضرورية فقط. يوجد حجز مفتوح واحد للرحلة. تستخدم قنوات الدفع قفل الرحلة نفسه داخل معاملة قاعدة البيانات؛ ويمنع القيد الفريد الموجود دفعتين ناجحتين للرحلة.

ينشأ مرجع جديد من `Guid` بصيغة `N` (32 محرفاً) لكل عملية سحب جديدة، ويبقى مرجع العملية المحفوظ ثابتاً في التحضير وحفظ المعاملة وتأكيد OTP. استرجاع عملية مفتوحة أو النقر المتكرر لا ينشئ مرجعاً جديداً ولا يعيد السحب؛ بعد إلغاء العملية أو رفضها قطعياً يحصل الطلب الجديد على مرجع جديد. رقم `transaction_id` في تأكيد فلوسك هو رقم المعاملة الذي أعاده المزود، وهو مستقل عن مرجع طلب التطبيق.

رد فلوسك المرصود في 2026-10-31 يرفض OTP بحالة HTTP 422 ورسالة `OTP number is not match with transaction id` وحقل `errors.OTP`، مع غياب `is_success` و`statusCode: null`. تعيده DLL الحالية كاستجابة غير مفهومة. يعالج الربط هذا العقد المحدد في خطوة الإكمال فقط كرفض لرمز التأكيد (`Failed` / `verification_failed`) ويعرض السبب بالعربية، بما يسمح بطلب جديد بمرجع جديد. لا يحفظ جسم الرد أو الرمز، ولا يعيد إرسال التأكيد. الاستجابات غير المطابقة أو المتعارضة أو أخطاء الاتصال تبقى غير محسومة. لا يثبت هذا الرد وحده سبب اختلاف الرمز؛ اختبار HTTP مع DLL الفعلية يتحقق من ثبات مرجع الطلب وإرسال رقم المعاملة الصحيح عبر جميع الخطوات.

بعد تأكيد المزود تحفظ الحالة الداخلية `ProviderSucceeded` أولاً. ثم تنفذ معاملة محلية واحدة تضيف `PaymentTransaction`، قيد حساب التسوية `1200-PM-{paymentMethodId}` مقابل حسابات الخدمة والعمولة، صافي مستحق السائق إلى محفظته وسجل التسوية، وتغلق المطالبات النقدية القديمة. تصبح الحالة `Succeeded` بعد حفظ جميع تلك الآثار. لا يخصم شيء من محفظة الراكب الداخلية. يبقى إكمال الرحلة التشغيلي بيد السائق.

ترفض قنوات الدفع والتحصيل النقدي أي محاولة أخرى أثناء العملية المفتوحة أو بعد الدفع. لا يسمح للعميل بتغيير حالة دفعة المزود إلى «مدفوعة» عبر `PaymentModel/update`. تمنع عمليات تغيير الأجرة والانتظار والإلغاء من السباق مع خصم لم تتضح نتيجته.

## الانقطاع والمراجعة

يعالج ربط جيب رد `success: false` مع `error.code` رقمي غير صفري و`error.message` وغياب `result` أو قيمته `null` في مساري `PCashoutInitial` و`PCashoutConfirm` كرفض صريح، حتى إن أعادت المكتبة `Unknown`. يشترط وصول رد واحد مطابق للعقد من المرحلة المطلوبة، وحالة HTTP 200 أو 400 أو 422، وعدم وجود إيصال مكتمل أو نتيجة نجاح متعارضة. جيب يعيد أيضاً HTTP 500 لرفض الأعمال: يقبل هذا الرد فقط مع غلاف ABP صريح (`__abp: true` و`unAuthorizedRequest: false` و`result: null`) وغياب إعادة توجيه `targetUrl`. رد نقص الرصيد الموثق بالكود الموجب `49` في التحضير يتحول إلى `InsufficientFunds`، ورفض رمز التحقق بالكود `-1005` في التأكيد يتحول إلى رفض الدفع. كلاهما يصبح `Failed` ويحرر اختيار طريقة دفع أخرى؛ يعرض تطبيق الراكب السبب بالأحمر وزر التغيير في النافذة والصفحة دون فتح تأكيد أو OTP بعد رفض التحضير. أخطاء HTTP 500 العامة أو الردود المتعارضة لا تحرر العملية. لا يستخدم نص الرسالة وحده لاتخاذ القرار، ولا يحفظ جسم الرد أو رمز العميل، ولا يعيد إرسال السحب. العمليات القديمة المحفوظة `ReviewRequired` تحتاج مراجعة رد المزود الأصلي قبل تغيير حالتها.

فتح صفحة الدفع أو إعادة الاتصال يسترجع العملية الموجودة. بعد إرسال طلب المزود لا يؤدي إغلاق HTTP إلى إعادة السحب. إذا نجح المزود وتعذر التسجيل المحلي، يبقى دليل النجاح محفوظاً ويعيد `GET` محاولة التسجيل المحلي فقط.

جلسات المكتبة ومعرفات سيرها في ذاكرة API؛ لا تستأنف جلسة رمز قديمة على عملية خادم جديدة. انتهاء جلسة قبل إرسال الرمز يسمح ببدء طلب جديد. أما انقطاع أو انتهاء مهلة بعد خطوة يحتمل أن تنفذ الخصم فيترك العملية `ReviewRequired` ويمنع الدفع النقدي أو خصماً آخر حتى مراجعة نتيجة المزود. لا تمسح هذا الحجز لمجرد انقطاع الشبكة. طابق مرجع الطلب/العملية مع سجل المزود قبل أي معالجة مالية يدوية. لا يوجد في هذا الإصدار مسار استرداد تلقائي من فلوسك أو جيب؛ تسلك إلغاءات الرحلات المدفوعة خارجياً مسار مراجعة الاسترداد الموجود.

## التحقق والتشغيل

تطبق ترحيلات قاعدة البيانات عند تشغيل API المهيأ. حافظ على إعدادات التشغيل ومفاتيح `security/wallet-keys` عند التحديث كما في [إعداد دخول المحافظ](wallet-login.md).

يعمل هذا الإصدار على عملية API واحدة لأن سير عمليات المكتبة في الذاكرة؛ التوسع إلى عدة عمليات يحتاج تخزين سير المزود دائماً أو توجيه الطلبات إلى العملية نفسها.

اختبارات التكامل تستخدم LocalDB مؤقتاً وبوابات مزود وهمية. اختبارات التطبيق تتحقق من ترتيب التأكيد والرمز والفاتورة، والاستعادة وحالات الشبكة ومنع التكرار. لم تنفذ الاختبارات خصماً حقيقياً؛ يلزم اختبار رحلة فعلي من الراكب باستخدام رمز فلوسك للتحقق من النتيجة لدى المزود.
