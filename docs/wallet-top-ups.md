# External-wallet availability and top-ups

The public payment catalog returns `isProviderConnected` only when an enabled account has a current authenticated runtime session for the configured version. `isServiceAvailable` additionally requires an active method and a supported withdrawal provider. No credentials, session token or login response are published. Connected methods sort first. Floosak and Jaib are supported by the current withdrawal integration; unsupported/offline methods remain visible, disabled with `الخدمة غير متاحة` in the passenger selector.

`POST /api/wallet/top-ups` accepts `paymentMethodId`, the user-entered positive `amount` (YER, maximum two decimal places), and a UUID `requestId`. It calls the exact same Request/Confirm/Complete withdrawal gateway used for ride payments. The user's registered mobile is authoritative: Floosak receives the Yemen prefix, Jaib receives nine local digits. A new attempt has a new UUID; replay keeps the original state, amount and account. One open top-up per passenger prevents concurrent withdrawals. A top-up does not reference or modify a ride.

Use `GET /api/wallet/top-ups/current` to recover the open operation, `GET /api/wallet/top-ups/{id}` for its state/invoice, or `GET /api/wallet/top-ups/by-reference/{UUID}` when a response was lost before receiving the operation ID. `POST /{id}/confirm` accepts `{approved:true|false}` and `POST /{id}/complete` accepts the requested verification code. Preparation can be abandoned before code dispatch. Provider-declared rejection releases the attempt. Uncertain dispatched debits remain recoverable and are never resubmitted automatically.

Only a validated final provider receipt can credit the internal wallet. One serializable transaction commits the external payment, wallet credit, immutable balanced journal, saved receipt and notification/outbox. The journal debits the external provider settlement asset and credits the customer's wallet liability for the exact top-up amount. Provider fees are disclosed separately; no driver settlement or ride revenue is created. A failed accounting commit preserves provider success and GET retries only local settlement.

The invoice records its number, customer, mobile, credited amount/currency, provider fees when known, request/provider references, completion time and original resulting balance. It can be reopened from the wallet movement. Notification delivery uses the existing realtime and persisted push mechanisms. OTP/PIN/voucher values are never saved in entities, local storage or receipts.

Deploy `ExternalWalletTopUps` with both Application and Database assemblies. The API applies the pending migrations on its normal startup. Tests cover the existing provider DLLs with mock HTTP, both top-up providers, exact-once credit/reference replay, authorization, failed accounting recovery and UI receipt rendering. They do not perform live withdrawals.
